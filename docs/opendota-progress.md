### 第一版模型会话接手入口

1. 从 GitHub 默认分支 `main` 读取工作区和仓库规则、本文、[采集与字段说明](opendota-collection.md)以及[验收快照](../samples/opendota/continuation-20261123.json)。采集仍由现有定时任务串行负责；模型会话使用已完成批次恢复数据。
2. 选择已发布的 DOTA 云环境，加载 `source /workspace/.cloud-environment/env.sh`，使用 `/workspace/.cloud-environment/onedrive-tools/onedrive_backup.py`。工具 SHA-256 应为 `3bbb9dc61f8e1e25cc2432514be128265ebc833940760a3bde09e130c0367408`，固定 rclone 为 1.76.0，授权变量为 `ONEDRIVE_RCLONE_CONFIG_B64`。普通续期产生 `vault_update_required=true` 可继续使用；凭据保留在仓库外。
3. 按快照 `completed_batches` 逐个恢复到新目录。下列命令示范第一批；其余批次替换 `--batch` 和 `--output`，不启动采集器：

```bash
source /workspace/.cloud-environment/env.sh
python3 /workspace/.cloud-environment/onedrive-tools/onedrive_backup.py restore \
  --batch ranked-official-20261112-1000 \
  --output data/model-source/ranked-official-20261112-1000 \
  --read-method graph-contentstream
```

4. `restore` 会回读并校验该批全部清单文件。继续将落盘 `manifest.json` 的原始字节 SHA-256 与快照 `manifest_sha256` 比较，将 `training/matches.jsonl` 的 SHA-256 与快照 `dataset_sha256` 比较，并核对 `training/report.json`、`training/audit.json` 的合格计数。完整原始归档保留在 `raw/`，需要独立重做来源审计时按[恢复说明](onedrive-backup.md#5-云端保存校验和取回)解压后使用现有审计脚本。
5. 通过后读取各批 `training/matches.jsonl`，按 `match_id` 合并。相同 ID 内容相同仅计一次，内容冲突则停止调查；复现本快照时去重数应为 **12404**。额外的测试副本、在途批次及失败读取不补入计数。
6. 每行 11 个字段：`match_id`、`start_time`、`game_mode`、`lobby_type`、`patch`、`rank_band_est`、`rank_known_players`、`radiant`、`dire`、`radiant_win`、`position_source`。双方英雄数组依次是官方 1～5 号位；`radiant_win` 是监督标签。最小行保存最终阵容和官方职责，ban 列表、选人顺序等特征需另行确认来源；预测输入限定为选人时可知的信息。
7. 首次模型实验记录所用批次、文件哈希、筛选口径和切分边界。按时间留出较晚数据，同一场的所有视角或增强样本归入同一份；分别报告两个版本和主要英雄／位置的结果。原先 35000／5000／10000 的训练、验证、测试数量是 **50000 场目标**下的规划，当前 12404 场需依据实际数量和版本覆盖重新确定切分。

## 合格的定义

- 详情为 `game_mode=22`、`lobby_type=7`；十个不同的正整数英雄 ID、双方各五个合法槽位、布尔胜负完整。
- 本节首批历史数据使用版本编号 60；2026-11-19 切换后新增使用编号 61。开始时间和时长有效，时长至少 720 秒。
- 元数据比赛 ID 相符，双方官方职责恰好各有 1～5 号位；不以 OpenDota 推断值补缺。
- 十人 `leaver_status` 都是整数 0 或 1；这允许曾断连的状态 1，不证明整场无人掉线。
- `?meta=1` 请求来源、原始响应 SHA-256、缓存、数据库和导出内容一致。

位置源是 Valve 元数据的 `lane_selection_flags`：1→1 号位、4→2 号位、2→3 号位、8→4 号位、16→5 号位。空的 6～13 队是元数据占位，跳过；缺失、多选或非单一职责不合格。该标记是官方职责记录，不能证明实际打法和站位。

最小数据保留十一个字段，双方英雄数组按 1～5 号位排序，并显式写入 `position_source=valve_metadata_lane_selection_flags`。近似分段沿用有效玩家大段位的较低中位数，同时保存已知人数。详见[采集与筛选规则](opendota-collection.md)。
