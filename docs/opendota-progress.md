# OpenDota 数据进展与初版方案

更新日期：2026-11-02（北京时间）。本文记录 OpenDota 主线目前已经完成的工作、已确定的数据口径和下一步计划。

## 1. 当前结论

采集、原始响应保存、字段整理和完整性检查已经跑通；初版先使用阵容、位置和胜负，配合模式、版本和近似分段。近似分段已接入采集脚本，并使用本地缓存回填了已有整理结果。

当前有 42 场天梯满足十个英雄、双方完整 1～5 号位和胜负齐全；按同版本、时长和离开状态进一步预筛后保留 41 场。这个样本量用于验证数据流程，尚不足以判断推荐效果。推荐模型尚未训练，APK 和网站尚未实现。

## 2. 产品与初版方向

- 输入：我方已选英雄、对方已选英雄、当前 ban 人和玩家自己的位置。
- 输出：最多 5 个推荐英雄，按玩家位置筛选候选英雄，排除已经被选或被 ban 的英雄。
- 初版方向：先积累对局，用阵容、位置、版本和分段学习与胜负的关系，再对当前 BP 下的候选英雄排序。
- 具体模型算法尚未确定，效果需要通过未参与训练的数据验证。

## 3. 初版数据结构

一场数据计划整理为以下最小结构。下面来自真实对局 9072646333；这是从采集结果整理出的训练样例格式，不是 OpenDota 原始响应的完整结构。

```json
{
  "match_id": 9072646333,
  "start_time": 1793594105,
  "game_mode": 22,
  "lobby_type": 7,
  "patch": 60,
  "rank_band_est": "冠绝一世",
  "rank_known_players": 10,
  "radiant": [48, 39, 97, 123, 131],
  "dire": [54, 74, 98, 27, 30],
  "radiant_win": false
}
```

| 字段 | 含义与来源 |
|---|---|
| `match_id` | 比赛 ID，用于去重及追溯原始对局 |
| `start_time` | 开始时间，Unix 秒；保留它便于按时间划分数据及核对版本 |
| `game_mode` | 游戏模式；初版筛选 22，即全英雄选择 |
| `lobby_type` | 房间类型；初版筛选 7，即天梯 |
| `patch` | OpenDota 版本编号；调查时的版本表中，60 对应 7.41 |
| `rank_band_est` | 根据已知玩家段位估算的整场大段位；无可用段位时为 `null` |
| `rank_known_players` | 参与分段估算的玩家人数，0～10 |
| `radiant` | 天辉英雄 ID，数组依次对应 1、2、3、4、5 号位 |
| `dire` | 夜魇英雄 ID，数组依次对应 1、2、3、4、5 号位 |
| `radiant_win` | `true` 为天辉胜，`false` 为夜魇胜 |

英雄 ID 对应关系可查 OpenDota 的 `/constants/heroes`。位置来自 `players[].position_est`，是 OpenDota 根据早期发育和分路推算的职责，可能误判；它不直接证明开局的物理分路。版本字段主要区分大版本，当前版本表没有细分字母小补丁。

初版只要求上述阵容及背景信息。采集器保留的其他列可以辅助复核，不把对线曲线或事件日志完整作为这版阵容样本的必要条件。

## 4. 近似分段规则

已在 `scripts/collect_opendota.py` 中实现：

1. 读取十名玩家中有效的 `rank_tier`；忽略空值、无效编码和未定级值。
2. 忽略星级，只保留先锋、卫士、中军、统帅、传奇、万古流芳、超凡入圣、冠绝一世八档。
3. 对已知大段位排序，取中位数；正好跨两档时取较低档。
4. 同时保存已知段位人数；少于 5 人时按“依据较少”解读。
5. 全部缺失时保存 `null` 和人数 0，不因此排除阵容样本。

该结果表示已知玩家资料所反映的整场大致水平。个人段位可能来自查询时的资料，不是对局当时的精确天梯分；冠绝一世也不能据此继续拆成 7000 分、10000 分等精确区间。

## 5. 采集链路与已完成工作

主线入口为 OpenDota 免费 API：

```text
GET /parsedMatches
  → 取得已解析比赛 ID
  → GET /matches/{match_id}
  → 筛选 game_mode=22、lobby_type=7
  → 检查十人英雄、胜负及双方 1～5 号位
  → 保存原始响应、来源和整理结果
```

`/parsedMatches` 包含多种模式，取得详情之后才能判断是否为目标天梯。已解析也不保证职责位置齐全，较短比赛可能没有位置估计。

采集脚本已支持：按 ID 去重、分页、限速、每日请求预算、缓存复用、断点续采，以及保存原始响应和 SHA-256。当前脚本最高允许约每分钟 50 次请求；免费接口仍有调用额度，应结合返回的限额信息控制采集。没有建立每日自动续跑任务。

采集器当前的 `matches.jsonl` 是关联的 `match` / `players` 结构，并输出比赛 CSV 和玩家 CSV。仓库中的样例进一步提取为第 3 节的最小格式；批量固定格式导出仍是后续工作。

## 6. 已验证的数据规模

截至本次记录，本地共保存 1100 场不同对局的原始详情，去重后统计如下：

| 检查项 | 场数 |
|---|---:|
| 天梯且十人英雄、双方位置、胜负齐全 | 42 |
| 再通过当前基础质量预筛 | 41 |

当前基础质量预筛条件为：`patch=60`、时长至少 720 秒、十名玩家的 `leaver_status` 均为 0 或 1。该检查用于排除明显不合适的记录，不证明位置估计准确，也不证明全部玩家全程正常参与。

41 场中，近似分段为冠绝一世 31 场、超凡入圣 5 场、统帅 4 场、万古流芳 1 场；38 场有十人的段位、2 场有九人的段位、1 场有四人的段位。样本仍少且偏高分段，不能据此判断全体天梯的英雄强弱或推荐效果。

已执行的验证：17 项自动化测试通过；已有 1100 场整理结果的分段字段及数据库、JSONL、CSV 一致性已逐场核对。近似分段回填全部使用本地缓存，原始响应和来源文件未改动。

## 8. 下一步

1. 继续用已解析比赛入口采集，按有效天梯样本数量统计效率和额度成本。
2. 统一批量输出第 3 节的最小结构，持续检查版本及分段覆盖。
3. 逐步向几万场规模扩充；免费额度下达到该规模的耗时尚未验证。
4. 数据规模足够后建立简单模型基线，并用独立对局评估，再接入 APK 和网页。
